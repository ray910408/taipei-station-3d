# 錨點的定義是「一份獨立證據」,不是「一台實體 AP」

指紋比對的評分公式（spec §3.2 的 `Σ_ap log N(rssi; mean, std) × w(detectRate)`）把每個錨點當成
獨立觀測相加，所以錨點存在的唯一目的是「不要讓同一份證據被重複加權」。我們因此定義**錨點＝一份
獨立證據**，判準是「訊號是否相關」；把多個 BSSID 併成一台實體 AP 只是達成它的手段，不是目的。

## 被否決的替代方案

**錨點＝一台實體機器**（CONTEXT.md 原本的寫法）。否決理由：它會把驗收標準導向「MAC 結構能不能
證明是同一台」，而那是無法驗證的——我們手上只有 MAC 位元這條間接證據，證不出兩顆 BSSID 是否裝在
同一個盒子裡。改用「獨立證據」後，驗收標準變成可操作的一句話：**併或不併，看它有沒有讓評分更準。**

## 後果

- **合併判準降級為代理指標。** 現行的 MAC 規則（OUI 同＋尾 3 bytes 差 ≤1 bit）不是定義，只是目前
  唯一算得動的近似。它已知會漏併「衍生 MAC」（廠商把 locally-administered bit 設起來另開 BSSID），
  2026-07-26 的家中實測顯示這讓 **16.7% 的 Top-15 欄位是重複證據**。這個缺口是**刻意保留**的
  （見 spec 決策記錄「待決 #4」），由 `tests/fp-real.test.ts` 的特徵測試主動追蹤——看到那條測試
  斷言「目前未合併」時，不要當成 bug 順手修掉。
- **資料驅動判準是後續選項。** 同樣的實測顯示，用兩顆 BSSID 的共同觀測點算 RSSI 相關性在 8 個 RP
  下完全無法分辨（確定同源的 r 低到 0.29，確定不同台的卻有三分之一超過 0.7）。但在 702 點的完整
  指紋庫裡可以改比「兩個錨點在全站 RP 上的完整剖面向量」，那是另一個量級的證據。第④包裁定時，
  候選不只是「哪條 MAC 規則」。
- **第②包的評分公式要知道它拿到的證據不完全獨立。** 在合併判準改善之前，同一條傳播路徑的衰減會被
  計入兩次，方向是過度自信。
