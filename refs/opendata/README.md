# 北捷開放資料（全路網 CSV）

原檔為 **Big5**，此處副本一律轉 UTF-8、內容一字未改（比照「原始資料永不修改」慣例）。
要重新下載時記得再轉一次編碼，直讀 Big5 會全亂碼。

檔案在 `refs/sources.json` 以 `trtc-od-*` 註冊，引用時就寫該 source id。註意那份表同時是
tracer 底圖選單的來源，非影像項目由 `isTraceable()` 濾掉（`tests/tracer-sources.test.ts` 守住）
——之後再往表裡加非影像來源時不必另外處理，但別繞過那個過濾。那裡的 `url` 是資料集
**頁面**而非直接下載連結（下載網址會隨版本變動，頁面才是穩定識別）。五個頁面都核對過標題、
提供機關與欄位清單與此處檔案相符：

| 檔案 | 資料集 |
|---|---|
| `exit-coords.csv` | [臺北捷運車站出入口座標](https://data.gov.tw/dataset/128428) |
| `exit-elevator-ramp-gps.csv` | [臺北捷運車站出入口無障礙電梯、無障礙坡道GPS座標](https://data.gov.tw/dataset/128414) |
| `accessibility-facilities.csv` | [臺北捷運車站無障礙設施資料](https://data.gov.tw/dataset/128416) |
| `elevator-locations.csv` | [臺北捷運車站無障礙電梯位置](https://data.taipei/dataset/detail?id=ba6b64b1-a387-4b34-93c6-7c3bf2dad3db)（只在 data.taipei，非 data.gov.tw） |
| `station-facilities.csv` | [臺北捷運車站設施資訊](https://data.gov.tw/dataset/128453) |

## 跨檔比對前必先正規化 join key

不正規化會爆假陽性（曾誤報 191 筆缺漏，實際 118 站完全對齊——這句話由稽核每次跑過）。
**下面這份清單由 `tests/opendata-joinkeys.test.ts` 現掃現比守住**——它把異常集合凍結起來，
原檔換版或掃描邏輯改動只要異常有增減就會紅，逼人回來更新這裡（這份清單手寫維護時錯過三輪）。

- 出口編號：去掉「出口」前綴、`單一出口`→`0`，其餘原樣保留。實際出現過四種形態：
  `出口1`／`單一出口`／`M2`（台北車站，兩檔都直接寫 `M*`、不帶前綴）／`2A`（含字母尾）。
  只處理前兩種的話，台北車站的兩部出口電梯會被當成無法解析而漏掉。
  **`單一出口`↔`0` 有一個例外**：奇岩站在 `exit-elevator-ramp-gps` 標「單一出口」，
  但 `exit-coords` 給的是出口 1／2／3、沒有 0 這筆——該列坡道無法用出口編號 join，
  只能靠座標就近配對。其餘 20 站的「單一出口」與「0」一對一對得上。
- 站名尾綴分三種寫法：
  | 寫法 | 檔案 | 例 |
  |---|---|---|
  | 無「站」字 | `station-facilities`、`elevator-locations` | `七張` |
  | 有「站」字 | `accessibility-facilities` | `七張站` |
  | 站名嵌在出入口名稱裡（帶「站」字） | `exit-coords`、`exit-elevator-ramp-gps` | `七張站出口1` |

  唯一的例外是**台北車站**——它本名就以「站」結尾，所以在無尾綴的兩檔裡也寫作 `台北車站`；
  無腦 `replace(/站$/,'')` 會把它砍成「台北車」。板橋另在 `station-facilities` 拆成
  `板橋(板南線)`／`板橋(環狀線)` 兩列。
- 站名異體字：Y19 幸福站在 `accessibility-facilities`／`elevator-locations`／`exit-elevator-ramp-gps`
  三檔都寫成 `幸褔`（示部），只有 `exit-coords`／`station-facilities` 是正確的 `幸福`。
  只修其中一檔仍會對不上；連帶後果是幸福站那部出口電梯連出口編號都 join 不回 `exit-coords`。
- 車站編號有兩處錯值、一處順序反轉、一處欄位個數不對（見下），拿編號當 join key 前先修。
  尤其 `accessibility-facilities` 的 `Line` 與 `Station_Number` **不能無條件 zip**：
  有一列的兩欄個數不同（松江南京），有一列順序相反（台北車站）。

## 已知原檔錯誤（刻意未修，用時自行處理）

1. `exit-elevator-ramp-gps`：圓山站出口2坡道 緯度 `250717908`，應為 `25.0717908`（掉小數點）
2. Y19 `幸褔站` → `幸福站`（異體字），出現在 `accessibility-facilities`、`elevator-locations`、
   `exit-elevator-ramp-gps` 三檔
3. `elevator-locations`：中山國中 車站編號 `BF12`，應為 `BR12`（文湖線編號一律 BR）
4. `elevator-locations`：七張 車站編號 `G03A`，應為 `G03`——`G03A` 是小碧潭，該檔內同編號對到兩站
5. `accessibility-facilities`：**台北車站那列的 `Line` 與 `Station_Number` 順序相反**——
   寫成 `淡水信義線/板南線` 配 `BL12/R10`，但實際是 淡水信義線＝R10、板南線＝BL12。
   直接把兩欄拆開對位 zip 會把兩條線的代碼互換。
6. `accessibility-facilities`：**松江南京那列 `Line` 只給一條、`Station_Number` 給兩個**——
   `中和新蘆線` 配 `O08/G15`。zip 會把 `G15`（松山新店線）整個丟掉或錯掛到中和新蘆線。
7. `station-facilities`：三和國中的「充電站」欄以 ASCII 單引號開頭（`'非付費區，近出口2`），
   Excel 匯出「強制文字」的殘留。五檔就這一處，直接拿去顯示會把引號一起印出來。

這份清單不是人工盤點出來的，是 `tests/opendata-joinkeys.test.ts` 掃出來的，逐項包含：

- 五檔的**標頭欄名與列數**（凍結在測試裡，不是拿進來的檔案自己的標頭當標準——整份一起
  少一欄時那樣看是自洽的；標頭逐欄比而非比接起來的字串，否則「用引號把兩個欄名併成一欄」
  接出來會一模一樣）、每列欄數（截斷的列不丟掉、直接當異常）、**CSV 語法**——引號要收尾、
  收尾後只能接逗號／換行／檔尾（`"月臺層"x`）、不能從欄位中途才開始（`月臺"層"`）；
  這三種寫法都不改變列數欄數，於是任何以列數欄數為準的檢查都看不見

讀這些 CSV 一律用 `tools/csv.ts` 的 `parseCsv()`，**不要 `split(',')`**——
出入口名稱若合法地帶引號含逗號，逐行切會整列錯位、那筆資料就安靜消失。
- 五檔**站名集合**是否對齊 118 站
- `Line`／`Station_Number` 的**欄位個數**與**對位順序**；線別寫法在兩檔查無對照也算異常
- 兩檔的每站**編號集合雙向比對**、同一編號對到多站
- 兩個出口檔的**出口鍵唯一性＋整組鍵的指紋**，以及 `station-facilities` 的**原始站名指紋**。
  唯一性只擋得住「撞成同一個鍵」，擋不住「改成另一個沒被用過的合法鍵」——ramp 側
  `出口1`→`出口2`、`板橋(環狀線)`→`板橋(錯線)` 都仍唯一、仍 join 得回去、正規化後仍是同一站，
  只有整組指紋看得出來
- `Line`／`Station_Number` 的**成分不得重複**（`文湖線/文湖線` 配 `BR13/BR13` 會 arity 相符、
  線別查得到、集合去重後也一樣，整條比較路徑都綠）
- `station-facilities` 的**原始站名唯一性**——板橋兩列帶線別（`板橋(板南線)`／`板橋(環狀線)`），
  正規化後會被站名集合收斂掉，換成彼此的複本時列數與站名集合都不動
- **座標值域**（抓掉小數點那種壞值）、**前導單引號**、**異體字**

上面七筆一筆不多一筆不少。重新下載後測試轉紅是正常的：回來核對差異、更新這裡與 `EXPECTED`。

幾個掃描本身踩過的坑，改動時留意：以前分次手掃時 3、4 靠集合比對找到、卻看不到 5
（集合相同只有順序反）；補上對位比對後又要小心別把「編號值本身就錯」的兩站誤報成順序錯，
所以順序檢查只在兩檔編號集合一致時才判定。而「查無對照就跳過」「欄數不足就過濾掉」
這類寫法會讓壞資料從所有後續檢查裡消失——一律當成異常報出來，別安靜略過。

`exit-elevator-ramp-gps`（電梯/坡道點）與 `exit-coords`（出口點）同編號座標差 40–140m 是
不同設施的正常位移，不是錯誤。
